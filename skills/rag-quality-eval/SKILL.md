description: Qualitative and quantitative evaluation of the zotero-rag query pipeline against a gold standard of 10 questions (easy verbatim to hard inference, in en/de/fr/es) over the public test-rag-plugin Zotero group. Asks which preset(s) to test, runs every LLM model of each preset separately, scores length, answer quality, source coverage, prompt-structure compliance, multilingual behaviour and groundedness, and has Claude judge semantic and inferred answers beyond regex matching. Use when asked to evaluate, benchmark, compare or regression-test the RAG pipeline, a preset, a model, a prompt change or a retrieval change; also for extending the gold standard.

# RAG quality evaluation

Runs a fixed set of gold questions through the real `POST /api/query` pipeline
(routing, retrieval, generation, citations) with `include_trace=true`, scores
each answer automatically, then **you** judge what string matching cannot see:
paraphrases, translations, correct attribution, and conclusions that must be
inferred. The library is the public Zotero group
[test-rag-plugin](https://www.zotero.org/groups/6297749/test-rag-plugin)
(`groups/6297749`, 61 entries, fully indexed). Per CLAUDE.md this is the only
library to use for live tests.

The skill runs inside the repository checkout and has the whole code base
available: the scripts import the backend's presets, credential checks and
citation regex where possible, and you should read the code (see "Diagnosing")
to explain a result, not just report it.

## Files

| Path | Purpose |
|---|---|
| `gold/questions.json` | the gold standard: 10 questions, facts with reasoning level, inference chains, judge notes |
| `gold/corpus.md` | the library's items, PDF keys and which questions use them (regenerated by a script) |
| `scripts/list_targets.py` | which presets/models can be evaluated, which cannot and why |
| `scripts/run_eval.py` | switch preset, query every model separately, save raw traces, score, restore preset, report |
| `scripts/judge.py` | prepare judging packets, validate/track judgments |
| `scripts/report.py` | aggregate to `report.md`/`report.json`, optional `--baseline` diff; re-scores saved runs |
| `scripts/scoring.py` | all criteria (pure functions, reusable) |
| `scripts/fetch_gold_corpus.py` | `verify` the gold facts against the real PDF text, `corpus` regenerate `gold/corpus.md` |
| `scripts/gold_tools.py` | `validate`, `format`, `stats` for the gold file |
| `references/criteria.md` | every criterion, its measurement and rationale, ideas not yet built |
| `references/judging.md` | the judging rubric and judgment file schema |
| `tests/test_skill.py` | unit + mock-backend end-to-end tests of the skill itself |

Make it discoverable as a Claude Code skill with
`ln -s ../../skills/rag-quality-eval .claude/skills/rag-quality-eval`
(or point a plugin at `skills/`). All commands below run from the repo root;
use `uv run python` for anything that imports backend code (project rule), plain
`python` is enough for `fetch_gold_corpus.py`, `gold_tools.py` and the tests.

## 0. Preflight

1. Backend up on the dev instance: `curl -s localhost:8119/api/config | head -c 200`
   (start with `npm start`). The run selects each preset in turn and restores
   the original state afterwards. With a Zotero identity key it uses *your own*
   preset choice (`PUT /api/config/my-preset`, docs/presets.md), which affects nobody
   else. Without an identity (typical loopback dev server) the only mechanism is
   the *server default*, which changes the preset for every client and the cron
   indexer while the run lasts: only do that on a dev instance, never on
   production, and tell the user before you start.
2. The gold library is indexed: `curl -s localhost:8119/api/libraries` lists `6297749`.
   If it is missing, index it first (plugin, or `bin/index_libraries.py`).
3. Keys (never print them). The Zotero identity key comes from
   `$RAG_EVAL_ZOTERO_KEY` or the encrypted key store (`bin/autoindex_add_key.py`);
   a loopback dev instance without `AUTHORIZED_GROUP_ID` needs none (then only the
   server-default mechanism is available). The backend does **not** read provider
   keys from its environment any more (docs/providers.md, credential scopes):
   for `user`-scope presets (KISSKI, OpenAI, Anthropic, Hugging Face, ...) the
   harness sends your key as a request header, taken from `$<KEY_NAME>` in the
   shell (e.g. `KISSKI_API_KEY`, `HF_TOKEN`) or from the key store, which holds
   one key per key name (`uv run python bin/debug_get_zotero_key.py --list` shows
   the names without values). `managed`/`shared` presets (RunPod as bundled,
   MPCDF) use the admin-set key on the server; nothing to send.
4. Sanity-check the skill itself: `python -m unittest discover -s skills/rag-quality-eval/tests`
   and `python skills/rag-quality-eval/scripts/gold_tools.py validate`.
   If the library changed since the gold file was written:
   `python skills/rag-quality-eval/scripts/fetch_gold_corpus.py verify`
   (needs outbound access to `api.zotero.org`).

## 1. Choose what to test (ask the user)

```bash
uv run python skills/rag-quality-eval/scripts/list_targets.py
```

It classifies every preset relative to the server's *default* preset and shows
each side's provider and credential scope: `active` (the preset your requests run
on now), `switchable` (compatible with the default, i.e. both sides remote and the
same embedding model, and every key it needs can be supplied), `credentials_missing`
(names the missing key names; export them or store them), `needs_restart` (a
different embedding model or a local-model side: the existing index would no longer
match; needs `MODEL_PRESET` + restart and usually a re-index, so it is **not**
evaluated automatically; tell the user).

Then use `AskUserQuestion`:

- **Which preset(s)?** Options: the active preset only / all switchable presets
  (recommended when comparing) / a specific one or several (list the switchable
  names). Always show what will be skipped and why.
- **Models:** each model of a preset is evaluated **separately**
  (`--models all`, default); offer `first` (preset default only) or a named
  list when the user wants a quick run. Providers with a live model list (KISSKI)
  are re-read after selecting the preset, with your key.
- **Repetitions:** default 1; suggest 3 when comparing close contenders or when
  the user cares about stability (router and LLM run at temperature 0.7).
- **Scope:** all 10 questions (default), or `--max-difficulty 3` for a smoke test.

Show the cost with a dry run before starting:

```bash
uv run python skills/rag-quality-eval/scripts/run_eval.py --presets all --dry-run
```

(5 KISSKI models x 10 questions = 50 queries per preset, plus one warm-up per
model; remote models can be slow or rate-limited, hence `--delay` and `--retries`.
Providers expose quota meters, `GET /api/rate-limits`: check them before a large
matrix on a metered key.)

## 2. Run

```bash
uv run python skills/rag-quality-eval/scripts/run_eval.py --presets <active|all|name,name> \
    [--models all|first|a,b] [--repeat 3] [--questions Q01,Q09] [--max-difficulty N] [--no-routing]
```

Output goes to `data/logs/rag_eval/<UTC timestamp>/`: `raw/` (one JSON per query:
response + trace, no keys), `meta.json`, then `results.jsonl`, `report.json`,
`report.md`. The original state (your own choice, or the server default) is restored
in a `finally` block; check the last `[INFO]` line, and if it says `RESTORE ... FAILED`
put it back manually. `meta.json` records how each preset was selected. An
interrupted run is continued with `--resume <dir>`. The one-line progress output
already shows verdict, recall, cited sources, words, detected language and latency.

Endpoint readiness is checked per preset (`GET /api/config/health`, the provider's
view): a `cold` endpoint (scale-to-zero) is woken with `POST /api/config/warmup`
and polled up to `--warm-timeout`; a `paused` one (stopped on purpose) or
`unreachable` one (nothing provisioned) is **skipped with the remedy** in the report
(resume/provision it in the plugin's Preferences or `bin/provision.py --preset
<name>`, then re-run with `--resume`). A `throttled` provider is a warning. Do not
trust the first latencies of a preset that was cold.

## 3. Judge (mandatory, this is where you use your reasoning)

The automatic scores are a **floor**: regex proves literal figures and names. A
correct paraphrase, a French/German/Spanish answer, a right fact attributed to
the wrong paper, or the conclusion a hard question is really asking for are
invisible to it. Judge every answered run:

```bash
python skills/rag-quality-eval/scripts/judge.py prepare data/logs/rag_eval/<run>
```

then follow `references/judging.md` for each packet: form your own expectation
from `minimum_answer` / `inference_chain`, give every gold fact a verdict
(`verbatim`, `semantic`, `inferred`, `partial`, `missing`, `contradicted`) with
evidence and an attribution check, list claims unsupported by the context file,
score citation support, inference quality (hard questions) and overall 0-5, and
write `judgments/<stem>.json`. For many packets delegate by preset/model to
subagents with the rules in `judging.md`; you stay responsible for the hard-tier
judgments. Track progress with
`judge.py status <run>` and finish with `judge.py validate <run>` (exit 0).

## 4. Report

```bash
python skills/rag-quality-eval/scripts/report.py data/logs/rag_eval/<run> [--baseline data/logs/rag_eval/<earlier run>]
```

Present `report.md` to the user in your own words, not as a table dump:

- ranking by composite, with pass/warn/fail counts and the per-tier split;
- **the criteria they asked for**: length, answer quality (judged recall, by
  reasoning level), sources found/cited, structural-guideline violations;
- **multilingual**: recall en vs non-en and answer-language match;
- **where quality is lost**: retrieval vs generation counts, regex false
  negatives/positives (how much the model's real quality exceeds string matching);
- stability, latency, errors, skipped presets and why;
- the three most useful concrete findings with the evidence (quote the failing
  answer or trace line) and a recommendation.

State clearly if some runs are unjudged (the report banner says so) and never
present provisional scores as final.

## Diagnosing a bad result (you have the code)

| Symptom in the report | Look at |
|---|---|
| facts lost in retrieval, `expected_doc_recall` low | `backend/services/rag_engine.py` (diversity floor, escalation, `_MAX_CHUNKS_PER_DOCUMENT`), `rag_agent.py`, preset `rag.top_k` / `score_threshold` / `max_chunk_size`, `document_processor.py` chunking, `embeddings.py` (multilingual model), `db/vector_store.py` |
| non-English recall far below English | embedding model of the preset (`intfloat/multilingual-e5-*` vs English-only), routing prompt language handling in `query_router.py` |
| facts lost in generation, answers too short | `_build_generation_prompt`, `max_answer_tokens` / `max_context_length` in the preset, model choice |
| no or malformed citations, `uncited_answers`, high retry rate | the CRITICAL CITATION RULE in `_build_generation_prompt`, `_missing_citations`/`_low_citation_diversity` retry guards in `rag_engine.py`, weaker models |
| wrong answer language | the "Respond in the same language" line in the prompt, model |
| `<think>` blocks, tool-call text, narration | reasoning models (deepseek-r1), `_looks_like_tool_call_leak`, answer post-processing |
| endpoint paused/cold/unreachable, 429/503 on one preset only | the provider layer: `backend/providers/` (`health`, `classify_http_error`, `parse_usage`), `docs/providers.md`, `services/endpoint_cache.py` |
| a user's query ran on a different preset than expected | `services/effective_preset.py` (default vs. saved choice, compatibility), `api/config.py` (`my-preset`) |
| routing surprises (`agents` is not `["rag"]`) | `query_router.py`, `query_orchestrator.py`, `docs/query-routing.md` |
| one query to investigate | `scripts/debug_live_query.py "<question>" --repeat 3` (CLAUDE.md "Live Query Debugging") and the saved `raw/*.json` trace |

Propose fixes with the evidence; do not change pipeline code unless asked.

## Maintaining and extending the gold standard

The gold set is a sample (10 questions over 10 of the library's 50 top-level
items). To grow it with more questions from a larger corpus, repeat the method
used when it was created. Keep this order; each step has a script or a check.

### How the current set was built (this session, 2026-10-10)

1. **Get access to the corpus.** The sandbox's network policy blocked
   `zotero.org`; the user had to allow `api.zotero.org` (and `www.zotero.org`).
   Check first: `curl -sS -o /dev/null -w '%{http_code}' https://api.zotero.org/groups/6297749/items?limit=1`.
2. **Retrieve all metadata** (public group, no key): paginate
   `GET /groups/6297749/items?format=json&limit=100&start=N` until a short page.
   Result: 111 records = 50 top-level items + 45 attachments + notes; 41
   items with a PDF attachment. `fetch_gold_corpus.py corpus` now regenerates
   this listing as `gold/corpus.md` (key, type, year, authors, title, PDF key).
3. **Get the PDF text.** The attachment file endpoint (`.../items/<key>/file`)
   returned 404 without an API key. The public full-text endpoint
   `GET /groups/6297749/items/<attachmentKey>/fulltext` returns the text Zotero
   extracted from the same PDFs, which is what the backend indexes; use it
   (cache: `.local/rag_eval_corpus/`). With an API key the PDFs can be fetched
   from `.../file` if layout or tables matter.
4. **Survey, then sample deliberately.** Sort by size (5k to 240k characters),
   type (empirical studies with tables, surveys, reviews, technical preprints, a
   book chapter, a German chapter, a blog post), year and topic cluster
   (tool comparisons, usage surveys, altmetrics, AI/RAG tools, teaching).
   Sampling rules used: cover every cluster; prefer documents that overlap
   (storage limits appear in three papers; two papers disagree on Zotero's PDF
   import) because they enable multi-document questions; include library
   duplicates (two items hold the Lorenzetti paper, two hold PyZoBot) to test
   de-duplication; include long documents (HySemRAG 98k, PyZoBot 152k characters)
   so retrieval has to find a needle. Documents read this time: Fulbright 2024,
   Lorenzetti 2013, Jin 2026, Sarkar 2025 and Basak 2014 in full; Cai 2021 and
   Li 2012 through their method/results/discussion sections; Chen 2018, PyZoBot
   and HySemRAG by abstract plus targeted searches for the facts used. Reading
   depth is a limit of the gold set: facts outside what was read are not covered.
5. **Read, and harvest facts while reading.** Read abstract, results, tables
   and discussion in full; for every candidate fact note document, location and
   exact wording, and classify it: *verbatim* (a figure or name that can be
   matched literally), *semantic* (a statement a model will paraphrase or
   translate), *inference* (nobody wrote it; it follows from combining sources,
   e.g. two papers that contradict each other, or a causal "why" assembled from
   two documents). Also note near-misses a weak model will confuse (47% vs 52%,
   300 MB vs 2 GB, which system has Neo4j) as `judge_notes`.
6. **Design the difficulty ladder.** 1-3: one document, answer is a literal
   figure in the abstract or results. 4-5: figures that sit in a table or need a
   little interpretation. 6-7: aggregation over several documents, or a question
   worded without the source's keywords ("do authors tell readers which software
   they used" instead of "underreporting"). 8-10: synthesis with conflicting
   evidence, a conceptual "why" that needs two papers, and a cross-system
   abstraction. Translate the *question* (not the facts) into de/fr/es for
   some items so cross-lingual retrieval and the answer-language rule are
   tested; keep the fact patterns language-neutral (numbers, names) or give
   alternatives per language. Per question write: `minimum_answer` (what any
   acceptable answer must contain), `facts` with `level`, `min_sources`,
   `min_distinct_cited`, a word band, `judge_notes`, and for hard questions an
   `inference` chain plus judge-only inference facts (empty `answer_patterns`).
7. **Write regexes conservatively and prove them.** Patterns must match the
   answer; `source_patterns` are the literal strings from the PDF text.
   `python skills/rag-quality-eval/scripts/fetch_gold_corpus.py verify` checks
   that every grounded fact occurs in its documents (36/36 passed; a deliberately
   broken pattern was confirmed to fail, so the checker is not vacuous).
   `gold_tools.py validate` checks schema, regex syntax, ascending difficulty,
   unique ids, >= 3 non-English questions, inference chains on hard questions.
8. **Test the harness, not the pipeline.** `tests/test_skill.py` drives the
   whole chain against a mock backend. Note the limit: this session had no live
   backend, keys or model access, so the gold set has not yet been run against
   a real preset; the first live run is also the calibration run (see below).

### Adding questions from a larger corpus

1. Refresh the listing: `fetch_gold_corpus.py corpus`; diff `gold/corpus.md`.
2. Cluster items by topic and pick 3-5 documents per planned question, using the
   sampling rules above. For a big corpus, delegate reading: one subagent per
   cluster, instructed to return **fact tables only** (document key, location,
   exact quote, whether it also appears or conflicts elsewhere), not questions.
   You compose the questions, because multi-document and inference questions
   come from comparing the tables, not from any single document.
3. Add the new documents to `documents` (item keys, attachment keys, exact
   title), the questions to `questions`, keeping existing ids stable and the
   file in ascending difficulty. Then `gold_tools.py validate`, `format`,
   `fetch_gold_corpus.py verify`, `gold_tools.py stats`, and the unit tests.
4. **Calibrate on a live run**: run the new questions with `--repeat 3` on the
   strongest available model and judge them. A fact no model ever gets is a bad
   question or pattern (or a retrieval/indexing problem worth knowing about);
   a fact every model gets trivially belongs one tier lower. Adjust the gold
   file, never the pipeline, to fix a bad question; record the change in
   `gold/CHANGELOG.md` and bump `version` (scores from different gold versions
   are not comparable; `report.py` shows the version).
5. Keep the set honest: do not tune prompts or retrieval against the questions
   you will score with (hold some questions out), never paste gold answers into
   prompts, tests or docs that the pipeline can index, and re-run `verify`
   after every library change or re-index.
