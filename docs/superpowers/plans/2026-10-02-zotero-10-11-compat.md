# Zotero 10 & 11 Compatibility Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the zotero-rag plugin work on Zotero 10 (current stable) and Zotero 11 (current beta/dev channel), fixing the specific APIs that the plugin calls which Zotero 10 removed or started throwing on, and clearing the manifest's version ceiling that currently rejects installation on Zotero 10 at all.

**Architecture:** Each removed/changed API the plugin actually calls gets a small, explicitly-marked backward-compatibility (BC) shim that feature-detects the new API and falls back to the old one. No big refactor, no dropped support for Zotero 7–9 — `strict_min_version` stays at `7.0`. Every fallback branch is tagged with a `// BC(<10):` comment so the whole set can be found with one grep and deleted together the day `strict_min_version` is raised past 9.

**Tech Stack:** Vanilla JS (bootstrapped Zotero plugin, no build step for `plugin/src/*.js`), Node's built-in test runner (`node --test`) with `vm`-sandboxed module loading (see existing `plugin/test/*.test.js`).

**Status: Tasks 1-4 complete.** See "Task 4 results" below for live-verification findings, including one correction to this plan's original research.

## The BC marking convention

Every fallback branch added by this plan carries a comment of the form:

```js
// BC(<10): <one-line reason>. Remove once strict_min_version is raised past 9.
```

`grep -rn "// BC(<10):" plugin/src` finds every shim this plan introduces. Do not use any other
marker — this is the only one in the codebase so far, and consistency is what makes the later
cleanup a one-line grep instead of a hunt.

### Task 1: Collection-pane selection-getter compat shim ✅

**Why:** `ZoteroPane.getSelectedLibraryID()` / `getSelectedCollection()` are still callable on
Zotero 10/11, but `collectionTree.jsx`'s `_requireSingleSelection()` (the method both delegate
to) does this (in the Zotero 11.0.SOURCE tree):

```js
_requireSingleSelection(name, replacement) {
    if (this.selection.count > 1
            || Zotero.isBetaBuild || Zotero.isDevBuild || Zotero.isSourceBuild) {
        throw new Error(`${name} was removed -- use ${replacement}`);
    }
    Zotero.Plugins.warnRemovedAPICall(name, replacement);
}
```

So on a **stable** Zotero 10/11 release with a single collection selected, the old call still
works (just logs a `Zotero.warn`, visible in the debug log). But it **throws unconditionally**
the moment the user selects more than one row, or the moment the client is a beta/dev/source
build — which is exactly the "dev channel" Zotero 11 build the issue (#44) says to test against.
`plugin/src/zotero-rag.js` calls the singular getters at 5 call sites, so on that dev channel:
`getCurrentLibrary()`, `createResultNote()` (the "Save as Note" button), and
`openFixUnavailableDialog()`/`_scanUnavailableCount()` (the Fix Unavailable Attachments button
and its badge) all throw immediately.

> **Correction found during Task 4's live verification (see below):** the actual installed
> Zotero 10.0.5-beta.2 build does **not** have the `|| Zotero.isBetaBuild || isDevBuild ||
> isSourceBuild` clause — only `this.selection.count > 1` throws there. That stricter,
> throws-regardless-of-selection-count check exists in the Zotero 11.0.SOURCE tree this
> research was based on, but apparently hasn't shipped to the Zotero 10 beta channel yet. The
> fix below handles both cases correctly regardless, but the severity on *today's* Zotero 10 is
> "breaks when the user multi-selects," not "breaks immediately on every beta build."

The replacement plural getters (`getSelectedLibraryIDs()`, `getSelectedCollections()`) were
**added in Zotero 10** — they don't exist on Zotero 7–9's `ZoteroPane`, so the fix must
feature-detect rather than switch outright.

**Files:**
- Modified: `plugin/src/zotero-rag.js` (added `_getSelectedLibraryIDCompat`/`_getSelectedCollectionIDCompat`; repointed 5 call sites)
- Tests: `plugin/test/zotero-rag.test.js` (+6 tests)

**Commit:** `3044d16` `fix(plugin): add Zotero 10/11 compat shim for collection-pane selection getters`

Implemented via subagent, spec-compliance reviewed (✅ pass), code-quality reviewed (✅ approved, one non-blocking minor note about undocumented first-ID-wins behavior on cross-library multi-selection).

### Task 2: Full-text search condition compat shim (`mentions.js`) ✅

**Why:** The citation/mention search feature builds a `Zotero.Search` with
`search.addCondition('fulltextWord', 'contains', term)`. The `fulltextWord` condition was
**completely removed** from Zotero's condition registry when full-text search was rewritten on
FTS5 (confirmed in `chrome/content/zotero/xpcom/data/searchConditions.js` — only
`fulltextContent` is registered now). Unlike the selection getters in Task 1, there is **no
warn-and-continue path**: `Zotero.Search.prototype.addCondition()` calls
`Zotero.SearchConditions.hasOperator(condition, operator)` first, which throws
`Error: Invalid condition 'fulltextWord' in hasOperator()` for any unregistered condition name,
unconditionally, on every Zotero 10/11 build (stable or beta). This is a hard, immediate break
of the whole "cites A and B" mention-search feature on Zotero 10+, not a future risk.

**Files:**
- Modified: `plugin/src/mentions.js` (added `FULLTEXT_SEARCH_CONDITION` feature-detected constant, wrapped in try/catch; updated doc comment and call site)
- Tests: `plugin/test/mentions.test.js` (+3 tests: fulltextContent-preferred, fulltextWord-fallback-when-absent, fulltextWord-fallback-when-throws)

**Commits:**
- `278ee4a` `fix(plugin): add Zotero 10/11 compat shim for fulltextWord search condition`
- `55526f8` `fix(plugin): harden fulltextContent detection against SearchConditions.get() throwing` (added after code review flagged that an uncaught throw during this module's load, via bootstrap.js's unguarded `loadSubScript()`, would abort the whole plugin's startup)
- `45dbcab` `test(plugin): cover the fulltextContent detection's throw/fallback path` (added after the final whole-branch review flagged the try/catch itself had no regression test)

Implemented via subagent, two review rounds (each found one real, fixed issue), final state approved.

### Task 3: Raise the manifest version ceiling ✅

**Why:** `plugin/src/manifest.json`'s `strict_max_version` was `"9.*"`. Stable Zotero builds
**enforce** `strict_max_version` at install time — independent of every code fix above, the
plugin was rejected outright on Zotero 10. This was the actual release-blocking part of #44's
"Zotero 10" half.

## Deferred — forward-looking risk, not a BC-fallback case

**Inline `<script>` blocks and one inline `onload=` handler in chrome XHTML.** Zotero 11's
underlying Firefox-153 base adds a baseline CSP on chrome documents that blocks inline
scripts/handlers — currently gated behind the `security.chrome_baseline_csp.enabled` pref
(not enforced by default yet, per the Zotero 11 developer page), so nothing is broken today.
Affected:

- `plugin/src/preferences.xhtml:8` — `onload="Zotero.ZoteroRAG.initPrefPane(window)"`
- `plugin/src/dialog.xhtml:11`, `plugin/src/setup-wizard.xhtml:10`,
  `plugin/src/fix-unavailable.xhtml:13`, `plugin/src/autoindex-status.xhtml:11` — inline
  `<script>` blocks that bootstrap-load `include.js`/the window's own script

This isn't a case of "old behavior to preserve with a fallback" — there's no old/new API split,
just inline-vs-external script loading, so it doesn't fit this plan's BC-shim pattern or its
Node-test-runner verification style (XHTML/DOM isn't exercised by the existing test harness).
Recommend a separate follow-up once Zotero publishes a firm enforcement timeline: move each
inline handler to `addEventListener` in an external script file.
